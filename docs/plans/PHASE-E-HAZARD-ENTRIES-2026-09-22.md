## What is being assessed

Today Lab Filing (W7) decides whether a report may be offered for one-click filing from a clinician-authored **filing profile** (`labfiling.profiles`): free-text `match` / `analytes` lists, per-profile `parameters` (normal ranges), trend and medicine guards, and an `allowComments` list. The suite pre-fills Medicus's filing screen and a human confirms (commit mode `manual` or `confirm` only — there is no full-auto mode).

Phase E lets the **approved Lab Result Catalogue** describe the same decision: results identified by SNOMED code, practice normal ranges per **result × lab × code**, safety guards per **result × lab**, lab comments per **lab × report group**, and one **assisted filing switch + one approval per test at a lab** (Medicus files a report group at once). It is delivered in stages: E0 adapter + parity tests (unwired); E1 **union-only** (the catalogue may only *add* blockers to today's gates) with a **separate mandatory shadow log**; E2 opt-in `filingEngine` pref (default legacy); E3 replacing the legacy gates — a separate CSO decision that needs a fresh assessment. The setup screens (v3.265.1–v3.267.0) exist and are inert: nothing reads them yet.

What does **not** change: the suite never files by itself (you press File, or press OK on a dialog listing every value — there is no automatic mode); a setup is inert until it has been reviewed and switched on (today on each machine — the practice-level version is the target in H-080 (e)); the whole-comment whitelist rule (v3.265.1); numeric-only "every numeric result needs a lab or practice range"; unreadable-row, ambiguity, unit-agreement and comparator-censored gates; the trend guard; medicine exclusions.

## H-080 — Lab Filing driven by the catalogue offers a one-click "all normal" that a human should have read

| Field | Value |
| --- | --- |
| **Hazard ID** | H-080 |
| **Description** | From Phase E the filing decision (whether a report is offered for one-click "normal, no action required" filing) can be made from the practice's approved Lab Result Catalogue instead of a filing profile: every result must be recognised **by SNOMED code**, belong to a report group for which assisted filing is **on and approved** at that lab, sit inside its practice range (or the lab's own flag), pass its guards (trend with direction, medicines) and have every lab comment covered by that group's allowed comments. The action offered is the same irreversible W7 write as today, and a human still presses File (manual) or confirms a dialog listing every value (confirm) — but a one-click that is offered wrongly is easy to accept, so a wrong offer is a hazard even though the software never files by itself. The new failure modes are: (a) the catalogue says a report is fileable when a result in it was never covered (the H-074 hole, now expressed through catalogue membership); (b) an approved catalogue entry (range, guard, group, allowed comment) is wrong; (c) migration from the legacy profiles silently loses a safeguard; (d) the catalogue and the legacy gates disagree and the catalogue wins. |
| **Potential causes** | A test's report-group mapping wrong or too broad, so a report is recognised as a covered group when it is not (including a heading that identifies more than one test); an analyte not declared in any approved group offered anyway (recognition by name rather than code); a range, guard or allowed comment approved without being read; a whole-comment whitelist entry that is itself unsafe; legacy profile → catalogue migration dropping an analyte, a guard (medicine, trend) or an allowed comment; the catalogue's opt-in engine replacing a legacy gate that would have blocked; approvals differing between machines in one practice; a stale or corrupt overlay silently changing recognition; a group switched on for a report layout it was never reviewed against (a lab changes its layout); one approval covering more than the reviewer saw. |
| **Affected users / components** | Every clinician who uses Lab Filing on an install that turns the catalogue engine on; indirectly every patient whose result is filed. Components: `shared/lab-filing-utils.js` (gate; new catalogue adapter), `content-scripts/triage-lens/lab-file-button.js` (engine selection, fallback, audit), `shared/lab-catalogue-overlay.js` (`filing.{ranges,guards,groups,screen}`, `filingStateForTest`, `approveFilingForTest`), `shared/lab-catalogue-core.js` (recognition), `options/investigations-section.js` (setup and approval), `shared/io/practice-profile.js` / `labcatalogue-io.js` (sync — arrive unapproved). |
| **Initial severity** | 4 (Major — filing a result as normal, no action, that needed a clinician's action; same consequence class as H-073 / H-074, an irreversible write to the patient record) |
| **Initial likelihood** | 3 (Possible — recognition and approvals now rest on practice-authored catalogue content that grows, and on a migration) |
| **Initial risk** | 12 |
| **Controls / mitigations** | (a) **In stages E1–E2 a report is offered only if BOTH engines allow it** — every legacy gate still runs unchanged (`requireRangeForAll` default true, unreadable-row, parameter ambiguity, unit agreement, comparator-censored fail-closed, H-074 unrecognised-analyte, trend, medicine exclusions, comment blocker, strictest-wins merging) and the catalogue's verdict is added to it, so the combined result can never be looser than today's. The catalogue's own **permissive** elements — the comments you allow through, a practice range, the lab-flag override — are therefore recorded by the shadow log but cannot excuse anything the legacy gates block until the legacy gates are replaced (E3); each is protected on its own (whole-comment matching and size floor, per lab × group, approved, unit-safe — controls j, k and H-081). Replacing a legacy gate (E3) is a separate CSO decision needing a fresh assessment of this entry. (b) **Separate, mandatory shadow log** recording, per evaluation, where the catalogue would have unblocked something legacy blocks or blocked something legacy allows — test / group names, codes, blocker reasons and counts only, **never values, patient or staff data**; reviewed before any engine change. (c) **Every result must be recognised by SNOMED code** and belong to an approved, enabled report group at that lab; anything unrecognised, ambiguous (two tests / two results tie, a code claimed twice) or covered by no approved group blocks the **whole task** — fail closed, never a pick. (d) **One approval for the test at the lab that covers everything it rests on** (its report group(s), the practice ranges and safety guards of its results, the group's comment settings, the Medicus wording if changed); given only from the test's own screen with the consequence stated next to the button; any change withdraws the affected item's approval and the test shows "awaiting approval". (e) **One version of the truth, set by the practice, approved by each clinician** *(target design — Nick, 2026-09-22; NOT yet implemented)*: the lab rules (ranges, guards, allowed comments, assisted filing switch) are set **centrally by administrator roles after appropriate practice discussion** and distributed by restore / sync so that every machine in the practice works from the same lab rules; each clinician then approves their own use of that single version, and changes to accepted ranges and results are decisions taken by the practice, not by an individual (an individual's local edit does not survive a practice-level decision). **Until that mechanism exists the operative control is that restore, sync, merge and import arrive unapproved on each machine** (the switch's intent may travel; the approval does not) and backups carry no approval or reviewer name — see the open review items. (f) **The suite never files by itself.** There are only two modes and this phase adds no third: in *manual* the suite pre-fills the Medicus filing screen and you press File; in *confirm* it shows a dialog listing every value with the limit it was checked against and the trend, and presses File only after you press OK. There is no automatic mode. (g) **Rollout and continuity (not itself a safety control):** some practices use the current filing profiles and moving to the catalogue needs set-up work, so the current engine is kept and stays the default. The catalogue engine is opt-in (`filingEngine`, default legacy, published through the practice profile) and becomes the default only after CSO sign-off of the new system; on any catalogue problem (missing, invalid, throws) the current engine is used, and disabling only ever makes the suite offer less. (h) **Migration is proposals only** and **refuses** any legacy profile with an analyte that cannot be mapped by code — the legacy profile keeps running; a parity test asserts every legacy `analytes` entry maps to a catalogue result of the target test. (i) **Audit records the engine, catalogue version and approval state** of the entry that made the offer, in the existing filing audit entry. (j) Whole-comment whitelist matching, size floor and no-truncation (v3.265.1, H-073). (k) The lab-comment settings are per lab × report group: a comment excused for one group is never excused for another. |
| **Residual severity** | 4 |
| **Residual likelihood** | 1 (in E1–E2 the catalogue cannot unblock anything the legacy gates block, a human still confirms, and nothing acts until approved locally) |
| **Residual risk** | 4 — **Proposed. Valid for the union-only stages only.** |
| **Acceptability** | **Proposed — pending CSO sign-off**, and **not live** until E2. Sign-off is requested for (1) the union-only rollout with a separate mandatory shadow log; (2) the shadow-log content (no values); (3) the exit criteria for E3 — a stated period with zero shadow disagreements in which the catalogue would have unblocked something legacy blocks, and a fresh assessment of this entry before any legacy gate is replaced. **Open review items:** control (e) is a target design, not yet implemented — until then approvals are per machine and a practice can run different acting catalogues on different PCs; how an administrator role is established and shown (who may set the practice's lab rules), and how the clinician is identified for per-clinician approval, are to be designed; whether the filing macro should refuse to run when this machine's catalogue version differs from the version the practice published or the one recorded at approval. |

## H-081 — A practice normal range or guard attached to a result acts where it does not belong

| Field | Value |
| --- | --- |
| **Hazard ID** | H-081 |
| **Description** | A practice normal range, trend limit or medicine exclusion is authored **per result** (and per lab), not per report group or test — the lab does not process ALP differently for an LFT and a Bone profile, so there is one ALP range, and editing it changes it wherever the result appears. The hazard is that such a value is applied where it is **not** valid: to a different lab (different assay, different reference range), to a different reporting form of the same analyte (HbA1c IFCC mmol/mol vs DCCT %, an eGFR equation), to a result that was mis-identified as that analyte, or in the wrong direction (a fall in eGFR treated like a rise). A range that is wrong in this way can make an abnormal value read "within my normal limits", the one place the suite's own judgement, rather than the lab's flag, decides normal. |
| **Potential causes** | A range typed for one lab used for a report from another; a range set for one code's unit applied to another code or to a value in a different unit (mmol/mol vs %); the unit of a code edited after the range was set; a result recognised by wording rather than code and given another analyte's range; a range shared across tests that one reviewer approved thinking only of one of them; a trend guard set with no direction (or the wrong one) so an improving value blocks — or a worsening one passes; a "practice range overrides the lab's own flag" setting that clears a flag the lab raised; a comparator-censored value (">47") or an urgent flag treated as inside a range; a typing slip in a bound. |
| **Affected users / components** | Clinicians using Lab Filing with the catalogue engine; patients whose results are filed. Components: `shared/lab-catalogue-overlay.js` (`filing.ranges`, `filing.guards`; `setFilingRange`, `setFilingGuards`, `filingStateForTest`), `shared/lab-filing-utils.js` (`profileParamBlockers`, `applyParamOverrides`, `unitsSafeToApply`, `trendBlockers`), `options/investigations-section.js` (results table, guards editor). |
| **Initial severity** | 4 (Major — a value that needed action read as within the practice's normal limits) |
| **Initial likelihood** | 3 (Possible — practice-authored numbers, several codes and labs per result) |
| **Initial risk** | 12 |
| **Controls / mitigations** | (a) **Keyed by result × lab × SNOMED code; the unit is carried by the code and snapshotted** in the range: if the code's unit later changes, the code leaves the result, the result or the lab is gone, the range stops acting and the settings page says why. A range can only be set on a code that is one of the result's own codes. **Codes and units are taken directly from lab reports** (learned by the scan, not typed), so there is no transcription or typographical error in them; and because a result is identified by its **SNOMED code rather than its wording**, there is no risk of a partial text match to an inappropriate result. The one typed element is the practice's range bound, covered by (f) and (j). (b) **The unit must positively agree** at the point of use (`unitsSafeToApply`: both declared and equal, or neither declared) — anything short of a confirmed match refuses to apply the practice range and keeps the lab's own flag. (c) **A range never clears an urgent flag or a comparator-censored value** (">47" against a maximum of 47 blocks) — unchanged legacy behaviour, kept. (d) **The lab-flag override is an explicit, per-result-per-lab setting**, off by default, shown in the guards summary. (e) **The trend guard states its direction** — changed / increased / decreased — defaulting to "changed" (either way, the stricter reading); only an explicit choice narrows it. (f) **One approval covers what acts**: the practice ranges and guards of the test's results at that lab are part of the test's assisted filing approval and are listed as awaiting approval until approved; any edit to a range or guard withdraws that item's approval; a result shared by several tests shows "shared by N tests" so the reviewer knows the change is not local. (g) **Recognition by code**, not wording, for the results a range applies to; a result that is not recognised by code blocks the task (H-080 c). (h) **A range is optional**: without one, the lab's own reference range and flag decide (numeric results still need one or the other — `requireRangeForAll`). (i) The practice's lab rules are meant to be set centrally and shared so every machine uses the same version (H-080 e, target design); until then everything arrives unapproved on each machine on restore / sync / merge and backups carry no approval. (j) In the confirm dialog the limit each value was checked against is shown beside it. |
| **Residual severity** | 4 |
| **Residual likelihood** | 2 (typing errors and a wrongly reviewed shared range remain possible; they cannot act until approved on the machine, a human confirms with the value and limit in front of them, and the unit / direction / comparator gates are unchanged) |
| **Residual risk** | 8 — **Proposed** |
| **Acceptability** | **Proposed — pending CSO sign-off.** Open review items: whether a range change on a result shared by several tests should require each affected test to be re-approved rather than only the one being edited; whether the confirm dialog should also show the lab's own reference range beside the practice range when they differ. |

## Addendum to H-073 — comment allow-list is now per lab × report group and lives in the catalogue

*(Add to the existing entry; the v3.265.1 matching change and the 2026-09-22 corrections are already recorded there as controls (h) and (i).)*

- **Description addition:** from Phase E the allowed comments are held per **lab × report group heading** in the catalogue (`filing.groups[].allowComments`), not per profile: a lab comment arrives as one package for a lab-defined group and only sometimes names a result, so the whole report is blocked unless the comment is allowed. They are approved with the test's assisted filing approval; today an entry arrives unapproved on each machine on restore / sync, and the target is practice-set rules that each clinician approves (H-080 e).
- **Control addition (l):** the same matching rule and size limits apply (whole comment explained, at least 6 words and 30 characters, not made only of generic words, at most 2 000 characters, refused rather than truncated); "never offer to file when the comment says…" phrases are per group as well. The legacy per-profile `allowComments` is unchanged until migration and keeps working in parallel.
- **Open review item (carried):** approvals are per machine; practice-level approval (maintained and enforced centrally, polled out) and per-clinician turning on are planned, not implemented.

## Addendum to H-074 — the "every result must be a declared analyte" gate becomes "every result must be recognised by code"

- **Control addition:** under the catalogue engine the H-074 gate is generalised: every result in the report must be recognised **by SNOMED code** and be a member of a report group for which assisted filing is on and approved at that lab; a result recognised only by wording, or by no approved group, blocks the whole task. In E1–E2 the legacy `unrecognisedAnalyteBlockers` still runs as well, so the gate can only tighten.
- **New failure mode recorded:** a legacy → catalogue migration that silently drops an analyte reopens exactly this hole. Control: migration is proposals-only and refuses any profile with an analyte that cannot be mapped by code (H-080 h).
